### 4. Time lines
- Each time line: minutes with raw in brackets, then `full days total: N`, then `XX days XX month XX years` (days first, years last). 1 year = 365 days, 1 month = 30 days (approximation, leap years ignored, agreed).
- `full days total` (only for LBC1 time and LBC2 time) = `ceil(minutes / 1440)`. Pack time has no full days total.
- Example: Time 2201920 min = `1530` full days = `9 days 2 month 4 years`. Pack time 1923803 min = `0 days 8 month 3 years`.
- The owner example (3 years 1 month 1 day 1000 min = 397) does not match: 1 year 1 month 1 day 1000 min = 397; 3 years 1 month 1 day 1000 min = 1127.

### 5. Box "Time since first installation" (days + minutes)
- Fields: **days** (input with Set in front) and **minutes** (0 to 1439), then the hint `(see LBC1 time $9261 full days total, press Set)` (wording by Claude; **without "add 1"**, owner 18.11.).
- **At every boot** (stays, owner: "very important"): minutes = 0, days + 1, days stored in NVM **before** 0x376 is sent.
- While running: the minutes counter counts with the vehicle clock; at 1440 days + 1, days stored in NVM, minutes restart at 0.
- **Every Set click writes the typed value to the NVM at once.**
- **Warning only (owner, 18.11.):** if the typed days are lower than `ceil(LBC1 minutes / 1440)`, the page shows a warning next to the field (proposal for the text: `Warning: days are lower than the pack time, the time may run backwards.`). The value is stored anyway, nothing is rejected.
- Never backwards: at boot at most 1439 minutes are lost and a full day is added, so the sent time always grows.
- Start value of 0x376 = `days * 1440 + minutes`. Limit: 24 bit, maximum 16 777 214 min (about 11 650 days), `0xFFFFFF` invalid.
- Replaces today's start (`seed_376_time()`, pack `$9261` + 2 min, `.cpp:131-141`) and the RAM clock (`.cpp:1265`).

### 6. Box "Distance since first installation"
- Input field with Set in front, then the **unit of LBC1** (same unit as the LBC1 distance line), then the hint `(see LBC1 distance $925F add 5 press Set)` (owner wording).
- The user reads the LBC1 distance, adds 5, types it, presses Set. **Every Set click writes the value to the NVM at once.**
- **At every boot** (stays, owner: "very important"): +5 on the stored distance, saved in NVM.
- Used as start distance for 0x376 (replaces `manual_distance_dkm`, key `ZOEDISTDKM`).
- Measured side effect: the pack adds the difference times 1.6 at sleep (+100 sent = +160 km in `$91CF`), so +5 per boot is about +8 km on the pack side per boot.

### 9. Units
- **LBC2 distance** is always **km**.
- LBC1 distance unit by comparing the shown numbers, tolerance **1 %** (agreed): LBC2 = 1.6 x LBC1 gives **mi** emphasised; LBC2 = LBC1 gives **km** emphasised; neither gives no emphasis.
- The distance box takes the unit of LBC1.
- Basis: both DIDs hold the same counter (Pack 3: raw 36016004, LBC2 with offset `0x80000000`), LBC1 shown in 1/160 (miles), LBC2 in 1/100 (km). No odometer value needed (owner, taken as given).
- Remark: with today's scaling the "mi" case appears for Pack 2 and Pack 3 every time. Emphasis is a plausibility sign, not a measurement of the car's unit.
- Emphasis of the unit = **bold** (owner, 18.11.). It is visible because the rest of the line is normal weight (see item 3).

### 10. NVROL and the frame 0x376 switch (owner, 18.11.)
- When an NVROL reset is started, the frame **0x376 is switched off and the switch is set back to default off** (also stored in the NVM, key `ZOE376`), so that sensible days and distance can be entered again before the frame is turned on.
- Today: `reset_NVROL()` (`RENAULT-ZOE-GEN2-BATTERY.h:26`) only sets `UserRequestNVROLReset`. `transmit_can()` sends the NVROL frames (`.cpp:985-988`) and **keeps sending 0x376** if it is on. `frame_376_enabled` is not touched, so after the reset the old clock and distance would go straight into the freshly reset pack.
- Where: in `reset_NVROL()` set `frame_376_enabled = false` and call `save_settings()`. The radio box then shows off after the next page reload.
- Dala's own note in the driver (`.cpp:14-16`): after resetting the NVROL you must enable "temporisation before sleep" and then stop streaming 0x373. This is not part of this item.
- **Stored days and stored distance stay in the NVM after NVROL** (owner, 18.11.). The frame is off then, so they have no effect until the owner turns it on again. (NVROL zeroes the pack's own values, `BEFUND_Echter_Bus_LBC_EVC_09-10.md:265`.)

## Facts from the Renault DDT file of the Zoe Ph2 MCPU (18.11.2026, `QUELLE_DDT_MCPU_Zoe_Ph2_Auszug_18-11.md`, read, not tested on a device)
- `$925F` "Distance Totalizer (vehicle)" is **km, step 0.01** (32 bit signed). So the register holds **360160.04 km** for Pack 3 (raw 36016004); our "225100.02 mi" in the LBC1 line is **raw / 160**, a conversion (km / 1.6). The frame 0x376 value 225100 became exactly 360160 km (factor 1.6).
- `$91CF` "Battery mileage": km, step 1/32, offset 0x80000000 (formula confirmed). `$9261` = absolute time of vehicle **saved** (min), `$91C1` = pack time **since 1st power-up** (min).
- Open for the owner: the LBC1 distance line shows `mi` (a conversion). The register unit is km. Keep the `mi` line as decided, or show `km` with the raw value and the `mi` in brackets? Not changed.
- The Ph2 has a reset for Safety Mode 1: `31 01 B0 04 00` ("ResetSM1") after `10 03`; the reason is in `$9216`. Not part of this build list.

## Zum Bauen vorgemerkt (23.11., Nutzer-Vorgabe): zwei neue Sleep-Modi "... + BMS off" mit eigenem BMS-Power-Zyklus am Ende des Sleep-Zyklus
- **Anlass:** Nutzung von Variante 1 oben (`bms_power_on()`/`bms_power_off()` aus der Zoe-cpp aufrufbar) fuer einen eigenen, an unseren Sleep-Zyklus gekoppelten BMS-Power-Zyklus -- unabhaengig vom generischen periodischen BMS-Reset.
- **Zwei neue Radio-Buttons, zweite Zeile unter der bestehenden "Sleep mode:"-Zeile (`RENAULT-ZOE-GEN2-BATTERY.cpp:933-937`), aber dieselbe Radio-Gruppe (`name='zoesleep'`), also weiterhin exklusiv mit den bestehenden drei Optionen (Sleep/Sleep 0x9281=1/9281 no 0x373 frame):**
  - `sleep_mode == 3`: "Sleep" + BMS off -- Vorlauf/Verhalten identisch zu `sleep_mode == 0` (kein `10 03`/`2E 92 81 01`, `sleep_state` startet direkt mit `LeadIn`).
  - `sleep_mode == 4`: "Sleep 0x9281=1" + BMS off -- Vorlauf/Verhalten identisch zu `sleep_mode == 1` (sendet `10 03`/`2E 92 81 01`, `sleep_state` startet mit `WaitIdle`).
  - Setter (`RENAULT-ZOE-GEN2-BATTERY.cpp:71`) von `(mode <= 2)` auf `(mode <= 4)` erweitert. Alle bestehenden `sleep_mode == 0`/`== 1`-Vergleiche im Vorlauf-Code (Zeilen 1801, 1814) muessen um `|| sleep_mode == 3` bzw. `|| sleep_mode == 4` ergaenzt werden, wo sie das Vorlaufverhalten steuern. Der `sleep_mode == 2`-Vergleich (0x373-Streaming-Bit entfernen, Zeile 1838) bleibt unveraendert -- 3/4 sind keine "9281 no 0x373 frame"-Varianten.
- **Neues Eingabefeld, direkt neben "Auto wake after:" (`RENAULT-ZOE-GEN2-BATTERY.cpp:944-947`, gleiche `<h4>`-Zeile):** Label **"BMS off after sleep:"**, Eingabe 1 bis 900 s, Default 600 s. Neue Route `/editZoeGen2BmsOffSeconds?value=X`, neues NVM-Feld (Vorschlag `ZOEBMSOFFSEC`), neue Konstante `BMS_OFF_SECONDS_MAX = 900`.
- **Ablauf, korrigiert (Nutzer, 23.11.): der Wake-Zyklus laeuft NICHT gleichzeitig mit dem BMS-off, sondern erst NACHDEM das BMS wieder Power hat.** Begruendung des Nutzers: das BMS bootet beim Wiedereinschalten komplett neu, unser eigener Wake-Zyklus (0x440 gestuft, 0x4CE-Pulse) soll sich daran orientieren wie ein ganz normaler, regulaerer Start -- nicht parallel zur stromlosen Phase vorgezogen werden.
  1. Bei `sleep_mode == 3` oder `== 4` wird **am Ende der Stille** (`sleep_seconds` abgelaufen) `bms_power_off()` aufgerufen (GPIO23 oder GPIO25, automatisch der richtige Pin via `esp32hal->BMS_POWER()`). Unser eigener Sleep-Zustand bleibt dabei weiter in "Silent" (keine normalen Frames, wie waehrend der Stille) -- **kein** Uebergang in die Wake-Sequenz an dieser Stelle.
  2. Nach Ablauf der eingestellten "BMS off after sleep"-Sekunden (ab dem Ausschalten gemessen) wird `bms_power_on()` aufgerufen (GPIO23/25 wieder HIGH).
  3. **Erst jetzt**, sobald das BMS wieder Power hat, startet unser normaler Wake-Zyklus (derselbe `wake_rest_sent`-Block wie bei den bestehenden Modi, 0x440-Staging, 0x4CE-Pulse, 0x373 wieder an) -- wie ein ganz regulaeres automatisches Aufwachen.
  - **Bestaetigt (Nutzer, 23.11.): die beiden Zeiten addieren sich, laufen nacheinander, nicht parallel.** Gesamtdauer von "Sleep gestartet" bis "BMS wieder Power on" = `sleep_seconds` + `bms_off_seconds` (z. B. 600 s Stille + 600 s BMS off = 1200 s bis GPIO23/25 wieder HIGH, danach erst startet der Wake-Zyklus).
- **Fruehes Wake-up waehrend der laufenden BMS-off-Phase: Entschieden (Nutzer, 23.11.) -- BMS sofort wieder einschalten.** Wird waehrend der BMS-off-Zaehlung von Hand "Wake up" gedrueckt, bricht das die BMS-off-Phase sofort ab (`bms_power_on()` sofort, Zaehler verworfen) und der normale Wake-Zyklus startet dann sofort (wie Schritt 3 oben, nur vorzeitig ausgeloest). Ein fruehes Wake-up **waehrend der Stille** (vor dem natuerlichen Ende des Sleep-Zyklus, BMS-off hat dann noch gar nicht begonnen) loest kein BMS off aus -- das BMS-off startet ausschliesslich beim natuerlichen/automatischen Ende der Stille, nie bei einem Abbruch der Stille von Hand.
- **Technischer Plan (Felder, noch nicht eingebaut):** `bool bms_off_active`, `unsigned long bms_off_start_millis`, `uint16_t bms_off_seconds` (Settings-Wert, Default 600, Range 1-900). Start **statt** des bisherigen `wake_rest_sent`-Uebergangs, wenn `sleep_mode == 3 || sleep_mode == 4`: `bms_power_off(); bms_off_active = true; bms_off_start_millis = currentMillis;` -- der eigentliche `wake_rest_sent`-Uebergang (und damit 0x440/0x4CE) wird fuer diese beiden Modi an dieser Stelle zurueckgehalten. Ende im normalen 100-ms-Tick: `if (bms_off_active && currentMillis - bms_off_start_millis >= (unsigned long)bms_off_seconds * 1000UL) { bms_power_on(); bms_off_active = false; /* jetzt erst den regulaeren wake_rest_sent-Uebergang anstossen */ }`. Abbruch im "Wake up"-Pfad: `if (bms_off_active) { bms_power_on(); bms_off_active = false; }`, danach normal weiter in den Wake-Uebergang.
- **Noch zu klaeren vor dem Bauen:** exakte Stelle/Mechanik, wie der zurueckgehaltene `wake_rest_sent`-Uebergang (Schritt 3) nach Ablauf von `bms_off_active` bzw. nach einem Abbruch tatsaechlich angestossen wird, ohne den bestehenden Sleep-State-Automaten (`SleepState`-Enum) zu verdoppeln -- vermutlich ein neuer `SleepState`-Wert (z. B. `BmsOff`) zwischen `Silent`/`Fixed9281*` und dem Wake-Start, beim Bauen im Code gegenpruefen, nicht nur annehmen. Exakter Name/Ort des bestehenden "Wake up"-Abbruch-Pfads ebenfalls beim Bauen im Code nachsehen. Ob eine eigene Statuszeile ("BMS off, noch X s") gewuenscht ist -- vom Nutzer nicht verlangt, daher vorerst nicht vorgesehen.
- **Ergaenzt (Nutzer, 23.11.): waehrend des gesamten Zyklus (Stille UND BMS-off-Phase, Schritte 1+2 oben) soll zusaetzlich dasselbe passieren wie beim generischen periodischen BMS-Reset -- Stroeme runterfahren und die Freigabe gegenueber dem Inverter wegnehmen.** Das ist exakt `setBatteryPause(true, false, EquipmentStop::UNCHANGED, false)` (`safety.cpp:560-594`: setzt `max_discharge_power_W`/`max_charge_power_W` auf 0, `emulator_pause_request_ON = true`), dieselbe Funktion, die `start_bms_reset()` selbst aufruft (`comm_contactorcontrol.cpp:579`). Vorbild in einer anderen Batterie-Datei vorhanden: `MEB-BATTERY.cpp:9` inkludiert `../devboard/safety/safety.h` und ruft `setBatteryPause(true/false, false, UNCHANGED, false)` an zwei Stellen auf -- gleiches Muster fuer die Zoe-Datei uebernehmbar (neuer Include, kein Eingriff in `safety.*` noetig).
- **Entschieden (Nutzer, 23.11.): nur die beiden neuen Modi 3/4 bekommen die Pause.** Die drei bestehenden, schon gebauten und getesteten Modi (Sleep=0, Sleep 0x9281=1=1, 9281 no 0x373 frame=2) bleiben unveraendert, keine Pause/Freigabe-Wegnahme bei denen.
- **Technischer Plan, ergaenzt:** `setBatteryPause(true, false, EquipmentStop::UNCHANGED, false)` beim Start des Sleep-Zyklus fuer `sleep_mode == 3 || sleep_mode == 4` (im Idle-Case von `handle_sleep()`, wo `sleep_requested` akzeptiert wird, analog zur bestehenden Stelle, an der auch `wake_4ce_pulse`/`wake_440_staging` zurueckgesetzt werden). `setBatteryPause(false, false, EquipmentStop::UNCHANGED, false)` erst am Ende, wenn der zurueckgehaltene Wake-Uebergang (Schritt 3 oben) tatsaechlich angestossen wird -- sowohl beim normalen Ablauf (BMS-off-Zeit abgelaufen) als auch beim fruehen manuellen "Wake up"-Abbruch.
